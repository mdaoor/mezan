11. Decision framework and the technical report template

11.1 Gate first, score second

Mixing hard constraints into a weighted sum lets a strong score on one axis buy back a disqualifying failure on another. Separate them:

StageQuestionOutcome
Hard gates (pass/fail)Data residency / external flag acceptable? Licence permits the use (including gated-access terms)? Fits the available GPUs/memory? Meets SLO at target concurrency? Safety bounds (hallucination, deletion, loops) met? Non-inferiority on critical slices met?Candidates that fail any gate are eliminated and listed with the reason
Scoring (survivors only)Given the survivors, which best balances accuracy, code-switch quality, throughput/cost and robustness?Ranked list + sensitivity analysis
Tie-breakersOperational simplicity, ecosystem/support, upgrade path, team familiarity, vendor riskWritten rationale

11.2 The weighted matrix (as implemented in Mizan decision_v1)

ComponentDefault weightDefinition (each in [0, 1], higher is better)
Accuracy50%1 − WER (evaluation runs against gold only; agreement-mode results are never called accuracy)
Code-switch20%mean of (1 − WER-AR), (1 − WER-EN), English-term preservation
Throughput20%best error-free (≤ 1% errors) RTFx across load steps, relative to the best candidate
Robustness10%mean of (1 − hallucination rate), (1 − insertion rate), (1 − failed-segment share)

Components with missing evidence are dropped and the remaining weights renormalised, and the report says so. Treat the matrix as a communication device, not an oracle:

  • Weights are value judgments. Show how the ranking changes as each weight varies (e.g. ±50% around the defaults, and the corner cases "accuracy only" and "throughput only"). A ranking that flips under mild perturbation is a tie; say so and decide on the tie-breakers.
  • Normalising throughput relative to the best candidate makes the score depend on who else is in the comparison; adding a very fast candidate lowers everyone else's throughput score. Report the absolute RTFx and cost per audio hour next to the score.
  • Linear scores treat a 1-point WER gain as equal at every level; if the use case has a threshold (e.g. "usable below 15% WER"), model it as a gate or a utility curve instead.

12.3 How to write the “why” so it survives review

Each recommendation in your technical report should have four parts: Claim (what you recommend), Evidence (the specific numbers with intervals and the run IDs), Uncertainty (what the intervals and slice sizes do not rule out; known limitations of the harness), and Reversal conditions (the measurable events that would make you switch back). Example form:

Claim: adopt model M on engine E with configuration K. Evidence: paired ΔWER = −x.x pp [lo, hi] (n = … segments, … words, cluster bootstrap by recording, 2,000 resamples, seed s); mixed-slice ΔWER = … […]; hallucination 0/… non-speech (≤ …% Wilson); p95 … ms / p99 … ms at concurrency c (3 repeats, open- and closed-loop); sustained RTFx …; cost per audio hour …. Uncertainty: dialect D has only … segments (indicative); loads measured on … hardware; gold-set drafted by system Y (blind subset agrees). Reversal: canary p99 > … for … min; human-sampled WER > …; any severity-1 hallucination.

12.4 Anti-patterns that produce confident, wrong decisions

  • Comparing a leaderboard number against your in-house number (different normalization, data, decoding).
  • Declaring a winner from a single run, a single seed, or a gold set built from the winner's own drafts.
  • Reporting mean-of-segment WER, or excluding the worst segments "as outliers" (loops and hallucinations are the product risk).
  • Optimising decoding settings on the same data used for the final claim.
  • Judging speed from a vendor README on different hardware, or from a closed-loop test at low concurrency.
  • Swapping the engine and the model in the same step and attributing the change to the model.
  • Treating "not significantly worse" on a small test set as "equivalent".
